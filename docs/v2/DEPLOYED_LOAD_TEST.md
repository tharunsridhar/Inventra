# Load test over a public HTTPS URL (2026-11-23)

Same scenario as [LOAD_TEST_RESULTS.md](LOAD_TEST_RESULTS.md), run against a
public HTTPS address instead of localhost. Read the setup section first,
because this is not a cloud deployment.

## Setup

- The app ran in the repo's own `docker compose` stack on a dev laptop:
  gunicorn (3 workers), Postgres 16, Redis 7, a Celery worker and Celery beat.
- A Cloudflare quick tunnel (`cloudflared tunnel --url http://localhost:8000`)
  exposed it at a random `https://<words>.trycloudflare.com` address.
  The address is temporary and changes every time the tunnel restarts.
- Every request therefore crossed the public internet and Cloudflare's edge
  before reaching the laptop. Latency includes that round trip.
- Machine: Intel Core i7-8665U (4 cores / 8 threads), Windows 11, Docker Desktop.
- Not a production topology. No Railway or AWS deployment existed at the time
  (the old AWS load balancer was gone and the Railway trial had expired).
- Locking was on (`INVENTORY_LOCKING_ENABLED` left at its default of `true`).
- Dataset: seeded demo data (501 products) plus the contended product
  `LOADTEST-CONTENDED-001`, reset to 100 units before the run.
- Auth: 60 employee tokens generated by `generate_loadtest_tokens`, picked at
  random per simulated user.

## Command

```
uv run python manage.py generate_loadtest_tokens
docker compose exec api python manage.py reset_loadtest_stock --stock 100
uv run locust -f loadtest/locustfile.py --host https://<tunnel-address> \
  --users 40 --spawn-rate 40 --run-time 30s --headless \
  --csv=deployed StockMutator
```

## Results

| Endpoint | Requests | Failures | RPS | p50 | p95 | p99 |
|---|---|---|---|---|---|---|
| `GET /products` (lookup) | 40 | 0 | 1.9 | 990 ms | 1200 ms | 1200 ms |
| `POST /sales-orders` (create) | 520 | 0 | 24.7 | 610 ms | 1200 ms | 1700 ms |
| `POST /sales-orders/{id}/complete` | 512 | 412 | 24.4 | 670 ms | 1600 ms | 1700 ms |
| **Aggregated** | **1072** | **412** | **51.0** | **640 ms** | **1500 ms** | **1700 ms** |

## Stock check (the part that matters)

| Check | Value |
|---|---|
| Starting stock | 100 |
| Completed sales | 100 |
| Ledger rows of type `sale` for the product | 100 |
| Final `current_stock` | 0 |
| Stock drop vs units sold | 100 vs 100, discrepancy 0 |
| Oversold (stock below zero) | none |

Confirmed two ways: a direct database query inside the api container, and
`GET /products/?search=LOADTEST-CONTENDED-001` through the public URL, which
returned `current_stock: 0`.

## Reading the error rate

Locust counts every non-2xx as a failure, so the headline rate is 412 of 1072
(38.4%). Almost none of it is a server fault:

- **0** responses were 5xx.
- **344** were `409 Conflict` on `/complete`. The contended product sold out
  after 100 completions, so every later attempt was correctly refused.
- **68** were `429 Too Many Requests` on `/complete`. That is the per-user
  `stock_mutation` throttle (20 per minute) firing for simulated users that
  share a token. It is the rate limiter working, not a defect.
- Of 512 completion attempts, exactly 100 succeeded, which equals the stock.

The sell-out also means the completion latencies above include many fast
rejections once stock hit zero. Treat the numbers as "what this stack does
under 40 concurrent buyers", not as a capacity estimate.

## Caveats

- Single run, 30 seconds. No repeats, so no variance estimate.
- Tunnel latency inflates every figure compared with a same-region cloud host.
- The earlier locked and unlocked comparison in
  [LOAD_TEST_RESULTS.md](LOAD_TEST_RESULTS.md) is unchanged. The unlocked run
  needs `DEBUG=true`, so it was not repeated here.
